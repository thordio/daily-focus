Context Scaling Proposed as New Frontier of AI Scaling

rss ArXiv cs.AI · 2026-11-27 · ⌛ 4 min read
Reason：Proposes a novel conceptual framework (context scaling) that could influence AI system design and research directions, addressing a common failure mode in deployed AI. High relevance for AI practitioners and researchers, though no experimental validation; no comments provided to assess discussion quality.
📰 What's New
arXiv preprint 2611.33160 introduces “context scaling” as a new frontier for improving AI systems by addressing mismatches between task-required state and available context. The authors frame a model as Pθ(d|c) and separate three budgets: training Bθ, decision-time Bd, and context-infrastructure Bc. They identify four failure modes—availability, fidelity, selection, and utilization—and organize current mechanisms into a five-operation context lifecycle with utility-cost curves for evaluation.
💡 Why It Matters： By making the model-infrastructure pair the unit of analysis, context scaling shifts attention from model weights and inference-time search to how systems acquire, represent, and deliver deployment state. This could redirect investment and system design for deployed assistants, coding agents, and sensor-driven applications where real-world failures stem from missing or distorted context rather than weak reasoning. It also outlines safety and governance needs for persistent, adaptive systems.
Background
Pretraining scaling invests in model parameters θ; decision-time scaling searches, refines, or verifies decisions under supplied context; context scaling improves the system’s capacity to acquire, represent, deliver, evaluate, and persist deployment state. Existing scaling paradigms target model weights and inference compute, but context scaling introduces a third budget Bc aimed at what the system can make available before a decision. The framework treats the model and its surrounding infrastructure as a single unit of analysis.
Key Details
The paper defines effective-context value as a task- and intervention-dependent attribution, separating deployment state from model-visible context. Its five lifecycle operations are acquisition, representation, delivery, evaluation, and persistence. The proposed evaluation methodology uses controlled budget interventions and utility-cost curves, with training, decision-time, and context budgets reported separately.

Partial Routing Delegates Subtasks to Cheaper Models, Boosting Agent Performance

rss ArXiv cs.AI · 2026-11-27 · ⌛ 4 min read
Reason：Novel method for resource-efficient agentic workflows with significant benchmark improvements (ViBench 70.2 to 78.5 at 19% lower cost); no comments provided to assess discussion quality.
📰 What's New
Researchers introduced partial routing, which guides a frontier lead model to delegate suitable subtasks to a cheaper worker model. On held-out ViBench tasks, with δ=0.75, partial routing raised mean task performance from 70.2 to 78.5 while lowering cost by 19%. On Terminal-Bench 4.0, it increased pass rate from 54% to 61% at similar cost. The lead model decides delegation during execution without any training.
💡 Why It Matters： This approach allows organizations to combine frontier model quality with cheaper model economics at a finer granularity than whole-task routing. For agentic workloads like full-stack app generation or terminal command tasks, the measured improvements mean fewer expensive API calls per completed task, potentially cutting inference cost while increasing success rates. Enterprises can implement it with no model retraining, lowering adoption barriers.
📊 Key Facts: 19% 54% 61%
Background
Model routing typically assigns an entire task to one model based on estimated difficulty and cost. In agentic workflows, however, a task may include both simple and complex subtasks, so a single model choice can be wasteful. ViBench is a benchmark where coding agents build full-stack web apps from a product requirements document, and Terminal-Bench 4.0 tests terminal command completion. Frontier models are high-capability, high-cost models, while worker models are smaller and cheaper.
Key Details
The delegation guidance is built from past runs by identifying recurring subtasks and measuring each model's quality and cost on them. A single hyperparameter δ controls the performance–cost tradeoff in the delegation policy. The lead model receives this guidance and decides delegation during execution; no model training is required. Giving the lead only the subtask breakdown, without a worker, also reduces cost on both benchmarks and raises Terminal-Bench pass rate.

Constraint-Aware Test-Time Scoring Framework Improves LLM and VLM Candidate Selection

rss ArXiv cs.AI · 2026-11-27 · ⌛ 6 min read
Reason：Presents a technical framework addressing known weaknesses in LLM/VLM candidate selection, with practical relevance for AI practitioners; no community discussion provided.
📰 What's New
A new constraint-aware test-time scoring framework for selecting among LLM and VLM candidate answers combines a small set of hard checks every answer must pass with a wider set of soft checks whose scores are blended into one number per candidate. The framework consists of three components: a drafting model that produces candidates, a configuring model that selects and weights checks for each task, and scoring models that rate properties no grounded tool can compute. The method was applied to CWEval, LIBERO with added safety variants, LiveCodeBench, and HotpotQA. An ablation study found that combining hard checks with candidate comparison lifts joint correctness-and-safety by up to +0.21 on retrieval-augmented QA and code-generation safety by up to +0.28 on CWEval, with gains tracking how weak the first sampled answer is.
💡 Why It Matters： For AI practitioners building systems that select among multiple LLM or VLM outputs, the finding that grounded hard checks plus candidate comparison deliver up to +0.28 improvements in code-generation safety and +0.21 in retrieval-augmented QA provides a concrete recipe: invest in hard constraint verification rather than complex soft-factor configuration. The per-task soft-check layer adding no measurable value suggests simpler alternatives are sufficient, potentially reducing implementation overhead for model selection pipelines in code, robotics, and QA domains.
📊 Key Facts: 0.21 0.28
Background
When an LLM or VLM produces several candidate answers, picking the best one typically relies on the model’s own confidence, a learned judge model, or a domain-specific check. Each approach has known weaknesses: an answer can be fluent but uncertain, mathematically plausible but physically infeasible, or rated highly by a judge while quietly breaking a task requirement. Constraint-aware scoring addresses this by requiring a small set of hard checks that every answer must pass, while blending softer property scores into a single per-candidate number. The test-time setting means the scoring happens after candidate generation, at inference time, rather than during training.
Key Details
The framework’s three components separate candidate generation, per-task check configuration, and property scoring. The ablation isolated the contribution of each component and found that the largest gains come specifically from combining hard checks with candidate comparison; the per-task soft-factor configuration layer added no measurable value over simpler alternatives. Evaluation tasks include CWEval for correct and secure code, LIBERO with added safety variants for robot manipulation, LiveCodeBench for competitive-programming hidden tests, and HotpotQA for retrieval-based question answering.
